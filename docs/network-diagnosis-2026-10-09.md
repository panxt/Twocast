# 2026-10-09 访问超时排查与调整

## 实测证据

使用用户已登录的 Chrome，经原有 ZeroOmega 代理测试，没有修改 VPN、代理规则或账号。

- 首页刷新：DOMContentLoaded 707 ms，load 2.62 s；5 条节目显示正常。
- 管理工作台切换：页面请求 584 ms；概览 API 509 ms；数据显示正常。
- 独立网络测试：经本机代理，TLS 建连约 2.3–2.5 s；无登录认证服务处理 0.4 ms；无效会话数据库检查 66.7 ms。
- 直连测试：8 s 连接超时，尚未到达应用。不能简单建议关闭代理。
- 生产历史日志：认证、列表、概览和团队接口发生过 300 s 的运行超时。这属于服务端故障证据，不能全部归咎于用户网络。
- 网络面板发现列表与导航触发多个自动页面预加载。扩展注入的资源不计为本站资源。

## 本次调整

1. 节目卡片、侧栏和顶部导航关闭自动预加载，点击时正常加载。
2. 生产 Postgres.js 连接池上限从 1 改为 3，降低单连接阻塞所有并发读取的风险；空闲回收 5 s，连接寿命 60 s，TCP keepalive 10 s；保持 Supavisor 事务池兼容设置和 8 s 建连超时。
3. 请求超时与网络失败显示中文解释；失败请求从去重表清除，重试可恢复。

这些是针对已识别风险的调整，尚未复现历史 300 s 超时，不能声称已证明其唯一根因。连接寿命和 keepalive 不是 SQL 执行时间硬上限。没有修改数据库全局超时或生产数据，也没有调用计费模型。

## 验证

- TypeScript 检查通过。
- 24 组、70 项 Jest 测试通过，包括超时后的重试恢复。
- 修改的生产文件 ESLint 通过；测试目录不在当前 ESLint 的 TypeScript 项目范围，使用 Jest 验证。
- 发布后的浏览器复测结果在任务汇报中记录。

参考：[Vercel 官方连接池建议](https://vercel.com/kb/guide/connection-pooling-with-functions)，包括避免连接池最大值为 1、降低空闲连接保留时间。现有代理可能增加额外连接延迟，后续如再次发生浏览器连接超时，应对照同一时间的 Vercel 请求记录判断是否到达服务。
